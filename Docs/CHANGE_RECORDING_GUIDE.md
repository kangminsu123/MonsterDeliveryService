# 프로젝트 수정 기록 가이드

작성 기준: 2026-10-15

앞으로 아이템, 전투 판정, 이펙트, 모델, UI 등 프로젝트를 수정할 때는 사용자가 다시 요청하지 않아도 이 가이드에 따라 기록한다. 사용자가 말한 문제와 실제 원인, 사용한 방법, 해결 결과를 실제 화면과 검증 근거로 남기는 것이 목적이다. 기준 예시는 [아이템 트러블슈팅 보고서](ItemTroubleshooting_20261015/README.md)다.

## 기록 대상과 작성 시점

- 버그 수정, 새 기능, 아이템 교체, 수치 조정, 효과와 화면 배치 개선을 모두 기록한다. 요구 변경과 결함 수정을 구분한다.
- 한 번에 받은 요청은 먼저 대조표에 나누어 적는다. 여러 요청을 한 사례로 묶더라도 요청별로 어느 사례에서 처리했는지 연결해 누락을 확인한다.
- 수정과 검증을 진행하면서 근거를 모으고, 작업을 사용자에게 넘기기 전에 기록과 보고서를 갱신한다.
- 후속 피드백으로 다시 고친 경우 같은 날의 사례에 변경 순서와 최종 값을 추가한다. 다른 날이면 이전 사례를 링크한 새 기록을 남긴다.
- 문서 오탈자처럼 게임 동작이나 화면에 영향이 없는 수정은 간단한 기록으로 충분하다. 실행 화면이나 게임 테스트를 불필요하게 만들지 않는다.

## 저장 위치와 기존 기록 보존

기존 `Docs/ItemTroubleshooting_20261015/`는 2026-10-15 기준 보고서로 보존한다. 후속 수정은 날짜별로 아래 구조를 사용한다. 같은 날에는 해당 폴더의 보고서에 계속 추가한다.

```text
Docs/ChangeRecords/YYYYMMDD/
  README.md              문제와 해결 과정을 적는 본문
  requests.csv           요청과 사례의 대조표
  ChangeReport_YYYYMMDD.docx
  index.html             이미지와 설명을 함께 읽는 열람본
  images/                당시 상태를 보존한 실제 캡처
  evidence/              검사 결과와 실행 로그
  source/                보고서 생성기와 편집 가능한 원문
```

일반적인 기능과 화면 수정은 위 보고서 형식까지 함께 갱신한다. 기존 보고서의 문장 구조와 페이지 구성을 재사용하고, Word 출력 후 각 페이지를 확인한다. 문서 생성기를 사용한다면 구조화된 원문도 갱신해 재생성할 때 내용이 사라지지 않게 한다. 단순 문서 수정은 README 기록으로 충분하다.

보고서 생성이나 캡처가 환경 문제로 불가능하면 가능한 본문과 근거부터 저장하고, 미완료 산출물과 이유를 `NEXT_SESSION.txt` 및 사용자에게 알린다. 캡처나 검증이 끝난 것으로 쓰지 않는다.

## 작업마다 수행할 순서

1. 사용자 요청과 기대 동작을 적고, 관련 코드와 기존 기록을 확인한다. 가능한 경우 수정 전 화면과 재현 순서를 보존한다.
2. 실제 원인을 확인한다. 확인한 사실과 추정을 구분하고, 원인을 모르면 미확인이라고 적는다.
3. 수정한 파일, 처리 흐름, 이전 값과 최종 값을 기록한다. 공통 구조를 사용했다면 재사용 경로와 예외 정책도 설명한다.
4. Unity 변경은 실제 Editor에서 확인한다. 로직 변경은 관련 기존 검사를 우선 실행하고, 새로 검사가 필요한 위험한 동작만 보완한다. 문서만 바뀐 경우 Unity 검사는 생략한다.
5. 수정 후 실제 화면을 캡처해 설명과 함께 배치한다. 이펙트는 본인 시점과 상대에게 보이는 모습, 충돌은 적중과 방어 또는 빗나감 등 해당 요청에 필요한 장면을 고른다.
6. 요청 대조표의 모든 항목을 해결 사례 또는 남은 제한에 연결한다. 보고서의 최종 수치를 코드와 대조하고 이미지와 로그 링크를 확인한다.
7. `NEXT_SESSION.txt` 맨 위에 요약, 보고서 경로, 검증 결과와 미완료 항목을 남긴다. 기획이나 현재 상태가 바뀌면 `GAME_DESIGN.md`, `TEAM_STATUS.md`도 갱신하고, 시각 변경은 `ART_REVIEW.md`에 근거를 연결한다.

## 캡처와 검증 근거 작성 규칙

- 게임 화면은 실제 Unity 캡처를 사용한다. 생성 이미지나 연출용 재구성으로 수정 전후를 대신하지 않는다.
- 캡처 직후 문서에 사용할 장면을 직접 열어 확인한다. 벽에 가린 상대, 효과가 끝난 프레임, 잘못된 아이템이나 UI가 나온 화면은 다시 촬영한다.
- 캡처는 `images/20261016_slime_after_local.png`처럼 실제 날짜, 대상, 상태와 시점을 구별해 저장한다. 원본 `art-review/`가 덮어써져도 당시 증거가 남도록 보고서 폴더에 복사한다.
- 수정 전 화면이 없으면 없다고 적고 이전 코드와 수치로 설명한다. 과거 자료는 촬영 날짜와 당시 상태를 표시한다. 파일명 날짜와 실제 재촬영 날짜가 다르면 실제 촬영 날짜를 별도로 남긴다.
- 검사 도구에서 상태나 위치를 설정해 재현한 캡처는 검수용 재현임을 표시한다. 정지 화면으로 판정 정확도나 시간 경과가 검증됐다고 주장하지 않는다.
- 검증은 실행 날짜, 메뉴 또는 명령, 통과 개수, 로그 경로를 남긴다. 과거 통과 기록과 이번 재실행을 구별한다. 실패 후 재시도했다면 실패 내용과 최종 결과를 함께 적는다.
- 미실행, 부분 확인, 실패, 해결 완료를 구분한다. 로컬 검사 결과를 온라인 동기화 완료로 확대하지 않는다. 겹치는 검사군의 개수를 고유 사례 수로 합산하지 않는다.
- 기절, 감속, 잉크, 강제 이동 등 공격 변경은 공통 피격 경로와 에어캡 방어, 면역을 확인한다. 해당 아이템의 예외 정책이 있으면 명시한다. 단순 화면 수정에 관련 없는 전체 검사를 반복하지 않는다.
- 문서 출력에 오류가 있으면 읽을 수 있게 고친 뒤 전달한다. 한글 누락, 이미지 잘림, 표 넘침, 캡션 분리와 페이지 누락을 확인한다.

## 사례 본문 템플릿

각 항목은 독자가 이전 대화를 보지 않아도 이해하도록 쓴다. 아래 틀을 복사하고 안내 문구를 실제 내용으로 바꾼다.

```markdown
## 사례 01 수정 내용을 설명하는 제목

작성 날짜: YYYY-MM-DD
관련 요청: R01, R02
분류: 버그 수정 / 요구 변경 / 수치 조정 / 연출 개선
상태: 해결 완료 / 부분 확인 / 미해결
이전 관련 기록: 해당하는 경우 상대 경로 링크

### 문제와 기대 동작

사용자가 겪은 현상, 발생 조건과 재현 순서, 기대했던 동작을 적는다.

### 원인

어떤 처리나 기준 때문에 문제가 생겼는지 코드와 관찰 근거로 설명한다.
추정만 가능한 부분은 추정이라고 표시한다.

### 사용한 방법

실제 바꾼 처리, 공통 구조 사용 방식, 이전 값 → 최종 값과 단위를 적는다.
관련 파일과 주요 함수 위치를 링크한다.

### 해결 결과

같은 조건에서 동작이 어떻게 달라졌는지 적는다.
남은 제한이나 미해결 조건이 있으면 함께 적는다.

### 실제 화면

![수정 후 본인 시점](images/YYYYMMDD_item_after_local.png)

캡처 날짜, 시점, 어떤 결과를 보여 주는지 설명한다.
필요하면 상대 시점, 수정 전 화면과 시간에 따른 장면을 추가한다.

### 확인 근거

- 실행 날짜와 Unity 장면 또는 환경:
- 실행 메뉴 또는 명령:
- 확인한 동작과 결과:
- 재시도한 경우 최초 실패와 최종 결과:
- 로그: [검사 결과](evidence/check-result.txt)
- 미실행 또는 남은 제한:
```

요청 대조표의 CSV 열은 `요청 ID,대상,요청 요약,관련 사례,처리 상태`로 유지한다. 요청 ID는 해당 날짜 보고서 안에서 중복되지 않게 부여한다. 이전 보고서를 참조할 때는 날짜와 사례 번호를 함께 쓴다.

## 전달 전 확인

- 요청마다 해결 사례나 남은 작업이 연결되어 있는가.
- 문제, 원인, 방법과 결과가 실제 코드 및 실행 근거와 맞는가.
- 최신 수치, 단위, 지속 시간, 시점과 실제 캡처 날짜가 정확한가.
- 기록 폴더에 이미지와 로그가 보존되고 링크가 열리는가.
- Word와 열람본이 편집 원문과 일치하고, 전체 페이지를 확인했는가.
- `NEXT_SESSION.txt`에 기록 위치와 검증 결과를 남겼는가.
